# 3.1 过期时间与内存淘汰

> 内存是有限的。本章回答两个问题：过期的 key 是**什么时候**被真正删掉的？内存满了 Redis 会**怎么办**？
> 这两个问题也是面试的常客。

## 1. 回顾：怎么设置过期时间

```
expire key 60            # 已有 key 设置 60 秒过期
set key value EX 60      # 存的时候顺便设置（推荐）
ttl key                  # 查看剩余时间（-1 永久，-2 不存在）
persist key              # 取消过期，变永久
```

一个容易踩的坑：**对已有 key 再次 `set`，过期时间会被清掉**！

```
127.0.0.1:6379> set token abc EX 100
OK
127.0.0.1:6379> ttl token
(integer) 98
127.0.0.1:6379> set token xyz          # 没带 EX 的 set
OK
127.0.0.1:6379> ttl token
(integer) -1                            # 过期时间没了，变永久了！
```

所以更新带过期时间的 key 时，要么重新带上 `EX`，要么用 `keepttl` 选项：`set token xyz keepttl`。

## 2. 过期的 key 是什么时候被删除的？

直觉上以为"一到点就删"，其实不是。给每个 key 挂个定时器太浪费资源，Redis 采用两种策略配合：

### 策略一：惰性删除（Lazy Expiration）

**访问 key 的时候才检查它过没过期，过期了就顺手删掉并返回 nil。**

- 优点：零额外开销
- 缺点：如果一个过期 key 永远没人访问，它就一直赖在内存里

### 策略二：定期删除（Active Expiration）

**Redis 每隔 100 毫秒随机抽查一批设置了过期时间的 key，把其中已过期的删掉。** 如果抽查发现过期比例很高，就再抽一轮，直到比例降下来。

- 优点：能清理没人访问的过期 key
- 缺点：是抽查不是全量，仍可能有漏网之鱼

### 小例子：亲手验证一次过期

不用背结论，30 秒就能亲眼看到"过期"的表现：

```
127.0.0.1:6379> set tmp 1 EX 2       # 存一个 2 秒后过期的 key
OK
127.0.0.1:6379> ttl tmp
(integer) 2                          # 还剩 2 秒
（等 3 秒再执行下面两条……）
127.0.0.1:6379> ttl tmp
(integer) -2                         # -2 = key 已经不存在了
127.0.0.1:6379> exists tmp
(integer) 0                          # 访问它，直接当不存在处理
```

注意两点：`ttl` 返回 `-2` 表示 key 不存在（`-1` 才是"存在但永不过期"，别搞混）；我们从外部**无法区分**"已被删除"和"过期了但还没轮到删"——对外表现完全等同消失。

两种策略结合，大部分过期 key 都能被及时清理。但注意结论：**过期 ≠ 立刻从内存消失**。极端情况下，过期但未被删除的 key 依然占着内存——这就引出了下一个保底机制。

## 3. 内存满了怎么办：内存淘汰策略

Redis 可以配置最大内存：

```conf
maxmemory 2gb
```

先看看你自己的 Redis 现在是什么配置（`config get` 支持一次查多个）：

```
127.0.0.1:6379> config get maxmemory maxmemory-policy
1) "maxmemory"
2) "0"                    # 0 = 不限制内存（默认值）
3) "maxmemory-policy"
4) "noeviction"           # 默认策略：内存满了直接报错
```

生产环境可以用 `config set` 在运行期动态修改，无需重启：

```
127.0.0.1:6379> config set maxmemory-policy allkeys-lru
OK
```

当内存用满，再写入新数据时，Redis 按 `maxmemory-policy` 配置的策略处理，共 8 种：

| 策略 | 行为 |
|------|------|
| `noeviction`（默认） | 谁也不删，直接对写命令**报错** |
| `allkeys-lru` | 从**所有 key** 中淘汰最久没被访问的 ⭐ |
| `allkeys-lfu` | 从所有 key 中淘汰访问频率最低的 |
| `allkeys-random` | 从所有 key 中随机淘汰 |
| `volatile-lru` | 只从**设了过期时间的 key** 中淘汰最久没访问的 |
| `volatile-lfu` | 只从设了过期时间的 key 中淘汰频率最低的 |
| `volatile-random` | 只从设了过期时间的 key 中随机淘汰 |
| `volatile-ttl` | 只从设了过期时间的 key 中淘汰最快要过期的 |

记忆方法：**前缀 = 淘汰范围**（`allkeys` 全部 / `volatile` 仅带过期时间的），**后缀 = 挑选算法**（LRU 最久未用 / LFU 最少使用 / random 随机 / ttl 最快过期）。

### 怎么选？

- **纯当缓存用**（数据丢了可以从数据库重建）→ `allkeys-lru`，最常用
- 既有缓存又有不能丢的数据 → `volatile-lru`，给缓存 key 设过期时间，重要 key 不设
- 默认的 `noeviction` 在生产上往往不合适——内存一满，业务写入直接报错

```conf
maxmemory 2gb
maxmemory-policy allkeys-lru
```

> 💡 LRU（Least Recently Used）：最近最少使用，"很久没人碰的先扔"。
> LFU（Least Frequently Used）：最不经常使用，"访问次数少的先扔"。
> 新手记住 LRU 即可，它是缓存领域最经典的算法。

## 4. 查看当前内存状况

```
127.0.0.1:6379> info memory
used_memory_human:1.20M        # 当前用了多少
maxmemory_human:2.00G          # 上限
maxmemory_policy:allkeys-lru   # 淘汰策略

# 查看单个 key 占多少内存
127.0.0.1:6379> memory usage user:1001
(integer) 88
```

## 5. 动手练习

1. 复现"set 覆盖丢 TTL"的坑：给 `token` 设置 100 秒过期，再用不带 `EX` 的 `set` 更新它，观察 `ttl` 变成了什么
2. 用 `keepttl` 保住 TTL：同样场景下改用 `set token xyz keepttl` 更新，验证过期时间还在倒数
3. 给一个带过期时间的 key 执行 `persist`，再用 `ttl` 确认它变成了 -1（永久）
4. 用 `memory usage` 分别查看一个短 key 和一个长 value 的 key 各占多少内存

<summary>参考答案</summary>

第 1 题（坑的复现——更新缓存时忘了带 EX，缓存变"永久"）：

```
127.0.0.1:6379> set token abc EX 100
OK
127.0.0.1:6379> ttl token
(integer) 99
127.0.0.1:6379> set token xyz
OK
127.0.0.1:6379> ttl token
(integer) -1                     # 过期时间被清掉了，变永久！
```

第 2 题（keepttl 保留原有过期时间）：

```
127.0.0.1:6379> set token abc EX 100
OK
127.0.0.1:6379> set token xyz keepttl
OK
127.0.0.1:6379> ttl token
(integer) 93                     # 值更新了，过期时间还在倒数 ✓
```

第 3 题（persist 移除过期时间）：

```
127.0.0.1:6379> set session:user1 data EX 60
OK
127.0.0.1:6379> persist session:user1
(integer) 1                      # 1 表示成功移除了过期时间
127.0.0.1:6379> ttl session:user1
(integer) -1                     # -1 = 存在但永不过期（注意不是 -2）
```

第 4 题（`memory usage` 返回字节数，含 key、value 和元数据的开销；短 value 有个几十字节的"底价"，value 越大占用越高）：

```
127.0.0.1:6379> set short hi
OK
127.0.0.1:6379> set big 0123456789...（粘贴一段约 100 字符的字符串）
OK
127.0.0.1:6379> memory usage short
(integer) 56
127.0.0.1:6379> memory usage big
(integer) 160
```

结论：再小的 key 也占几十字节（编码与元数据开销），key 名和价值不大的超长 value 都在白费内存。

## 6. 小结（面试就考这几句）

1. 过期删除 = **惰性删除 + 定期删除**，过期不等于立刻消失
2. 不带 `EX` 的 `set` 会**清掉**原有过期时间
3. 内存满了走**淘汰策略**，缓存场景推荐 `allkeys-lru`
4. 默认策略 `noeviction` 会让写入报错，生产环境要显式配置
