# 5.2 事务处理

> 转账转到一半程序崩了，钱扣了但没到账——事务就是防止这种惨剧的机制。本节讲透 SQLAlchemy 中事务的正确姿势。

## 一、什么是事务？

**事务（Transaction）= 一组必须"同生共死"的数据库操作。**

经典例子——转账：

```
① 从张三账户扣 100 元
② 给李四账户加 100 元
```

如果 ① 成功后程序崩溃、② 没执行，100 元就凭空消失了。事务保证：**要么两步都成功（commit），要么都不生效（rollback）**，不存在中间状态。

事务的四大特性（ACID）了解即可：**原子性**（全成或全败）、**一致性**（数据始终合法）、**隔离性**（并发事务互不干扰）、**持久性**（提交后断电也不丢）。

## 二、Session 的事务模型：你一直在用事务

关键认知：**Session 的所有操作天然就在事务里**。

```python
with SessionLocal() as session:
    session.add(user1)        # ┐
    user2.age = 30            # ├─ 同一个事务
    session.delete(user3)     # ┘
    session.commit()          # 三个操作一起生效
```

- 从第一个数据库操作开始，Session 自动开启事务
- `commit()` 提交事务；`rollback()` 撤销事务内所有未提交操作
- commit 后再操作，会自动开启**新的**事务

所以"把相关操作放进同一次 commit"不只是性能优化，更是**正确性保证**。

## 三、转账示例：事务的标准写法

```python
from decimal import Decimal
from sqlalchemy import String, Numeric
from sqlalchemy.orm import Mapped, mapped_column

class Account(Base):
    __tablename__ = "accounts"

    id: Mapped[int] = mapped_column(primary_key=True)
    owner: Mapped[str] = mapped_column(String(50))
    balance: Mapped[Decimal] = mapped_column(Numeric(12, 2), default=0)
```

### 写法1：try / except / rollback（基础版）

```python
def transfer(session, from_id: int, to_id: int, amount: Decimal):
    try:
        from_acc = session.get(Account, from_id)
        to_acc = session.get(Account, to_id)

        if from_acc.balance < amount:
            raise ValueError("余额不足")

        from_acc.balance -= amount
        to_acc.balance += amount
        session.commit()               # 两笔变动一起生效
    except Exception:
        session.rollback()             # 任何一步出错，全部撤销
        raise                          # 继续抛出，让调用方知道失败了
```

### 写法2：session.begin() 上下文（推荐）

`with session.begin():` 块结束自动 commit、异常自动 rollback，不用手写 try/except：

```python
def transfer(session, from_id: int, to_id: int, amount: Decimal):
    with session.begin():
        from_acc = session.get(Account, from_id)
        to_acc = session.get(Account, to_id)

        if from_acc.balance < amount:
            raise ValueError("余额不足")     # 抛异常 → 自动 rollback

        from_acc.balance -= amount
        to_acc.balance += amount
    # 走到这里 = 已自动 commit
```

也可以创建 session 时一步到位：

```python
with SessionLocal() as session, session.begin():
    ...  # 增删改，结束自动提交
```

> ⚠️ 用了 `session.begin()` 就**不要**在块内再手动 `session.commit()`，会报错"事务已由上下文管理"。

## 四、rollback 之后 Session 还能用吗？

能。rollback 会把 Session 恢复到干净状态，可以开始新的事务：

```python
with SessionLocal() as session:
    try:
        session.add(User(email="duplicate@example.com"))   # 假设撞了唯一约束
        session.commit()
    except IntegrityError:
        session.rollback()

    # session 依然可用，继续干别的
    users = session.scalars(select(User)).all()
```

但注意：**rollback 后，之前 add 但未提交的对象会回到瞬态（transient）——等于从没 add 过**，像一张还没寄出的草稿被整页撕掉，重试时重新构造对象即可；已加载对象的未提交修改也会一并撤销。别把它和**游离态（detached）**混淆：游离态是 `session.close()` 之后对象才进入的状态——对象和数据还在内存里，但已脱离 Session 管理，像离职员工，档案还在手上，公司不再替他同步。两者是不同时机的不同状态。

> 📌 复习一个 3.1 节的要点：commit 失败后**必须** rollback，否则 Session 卡在"故障"状态，后续操作全部抛 `PendingRollbackError`。

## 五、嵌套场景：函数里该不该 commit？

新手常见困惑：写了个 `create_user()` 函数，里面要不要 commit？

**最佳实践：底层函数只操作、不提交；由最外层的调用方统一提交。**

```python
# ✅ 推荐：CRUD 函数不 commit（最多 flush），提交权交给调用方
def create_user(session, name: str, email: str) -> User:
    user = User(name=name, email=email)
    session.add(user)
    session.flush()          # 需要立刻拿 id 的话 flush 一下
    return user

def create_post(session, user: User, title: str) -> Post:
    post = Post(title=title, author=user)
    session.add(post)
    return post

# 调用方掌控事务边界：用户和文章要么都建好，要么都不建
with SessionLocal() as session, session.begin():
    user = create_user(session, "张三", "zs@example.com")
    create_post(session, user, "第一篇")
```

如果每个小函数内部都 commit，就把一个完整业务拆成了多个独立事务，中途失败会留下"半成品数据"。

**一句话原则：谁代表完整业务，谁 commit。**（在 FastAPI 里，"一个请求 = 一个事务"，第 6 章的依赖注入正是这么设计的。）

## 六、并发问题初探：两个请求同时扣库存

```python
# 库存只剩 1 件，两个请求同时执行：
stock = session.get(Product, 1).stock    # 两边都读到 1
if stock > 0:
    product.stock -= 1                   # 两边都扣成功 → 超卖！
    session.commit()
```

两种经典解法，先混个脸熟：

### 悲观锁：SELECT ... FOR UPDATE

```python
with session.begin():
    product = session.scalar(
        select(Product).where(Product.id == 1).with_for_update()
    )        # 锁住这一行，其他事务读它会阻塞等待
    if product.stock > 0:
        product.stock -= 1
```

### 乐观做法：原子 UPDATE

```python
from sqlalchemy import update          # 用 update() 语句别忘了导入

result = session.execute(
    update(Product)
    .where(Product.id == 1, Product.stock > 0)     # 条件写进 SQL，由数据库保证原子性
    .values(stock=Product.stock - 1)
)
session.commit()
if result.rowcount == 0:
    print("库存不足，扣减失败")
```

> 💡 SQLite 对并发支持较弱（`with_for_update` 无效），这些技巧主要用于 MySQL/PostgreSQL。新手阶段知道"并发扣减要用锁或原子 UPDATE"即可，遇到再深究。

## 🎯 练习

**练习 1：扣库存 + 记流水，中途崩溃不留半成品**

建 `products`（id/name/stock）和 `stock_logs`（id/product_id/delta）两张表，写一个"扣库存并记一条流水"的函数（函数内**不 commit**）。先正常执行一次；再故意在扣减之后、提交之前 `raise`，最后查库验证：库存没变、流水只有成功那一次。

<details><summary>参考答案</summary>

```python
# stock_demo.py
from sqlalchemy import String, create_engine, select
from sqlalchemy.orm import (DeclarativeBase, Mapped, mapped_column,
                            sessionmaker)


class Base(DeclarativeBase):
    pass


class Product(Base):
    __tablename__ = "products"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50))
    stock: Mapped[int]


class StockLog(Base):
    __tablename__ = "stock_logs"
    id: Mapped[int] = mapped_column(primary_key=True)
    product_id: Mapped[int]
    delta: Mapped[int]


engine = create_engine("sqlite:///shop.db")
SessionLocal = sessionmaker(bind=engine)

# 每次运行都重置，保证输出可复现：1 号商品库存 10
Base.metadata.drop_all(engine)
Base.metadata.create_all(engine)
with SessionLocal() as session:
    session.add(Product(id=1, name="手机壳", stock=10))
    session.commit()


def deduct_and_log(session, product_id: int, qty: int) -> None:
    """底层函数只操作、不提交——提交权交给调用方（第五节的原则）"""
    product = session.get(Product, product_id)
    if product.stock < qty:
        raise ValueError("库存不足")
    product.stock -= qty
    session.add(StockLog(product_id=product_id, delta=-qty))


# 第 1 次：正常路径，两步一起提交
with SessionLocal() as session, session.begin():
    deduct_and_log(session, 1, 2)              # 库存 10 → 8，并记一条流水

# 第 2 次：扣减之后、提交之前，模拟崩溃
try:
    with SessionLocal() as session, session.begin():
        deduct_and_log(session, 1, 3)          # 内存中 8 → 5（还没提交）
        raise RuntimeError("程序中途崩溃！")    # → session.begin() 自动 rollback
except RuntimeError as e:
    print("捕获：", e)

# 验证：数据库里没有半成品
with SessionLocal() as session:
    logs = session.scalars(select(StockLog)).all()
    print("库存：", session.get(Product, 1).stock)     # 8（不是 5）
    print("流水条数：", len(logs))                     # 1（崩溃那次没留下）
```

预期输出：

```text
捕获： 程序中途崩溃！
库存： 8
流水条数： 1
```

要点：`with session.begin():` 块内任何异常触发自动 rollback，扣库存和记流水**同生共死**。反过来想：如果把 commit 挪进 `deduct_and_log` 里（每步一提交），崩溃时就只剩下"扣了库存、没有流水"的半成品数据了。

**练习 2：把 6.1 的内存版用户 API 改造成"一个请求一个事务"**

给内存版用户 API 换上 SQLite 存储，用**升级版 get_db**（接口正常结束自动 commit、抛异常自动 rollback）管理事务；再写一个"先 add 再故意 raise"的接口触发 500，最后查库确认没有半成品数据。（需要先读完 6.1；依赖注入的原理 6.2 详解，这里先照抄。）

<details><summary>参考答案</summary>

```python
# app.py
from typing import Generator

from fastapi import Depends, FastAPI
from pydantic import BaseModel
from sqlalchemy import create_engine
from sqlalchemy.orm import (DeclarativeBase, Mapped, mapped_column,
                            Session, sessionmaker)

engine = create_engine("sqlite:///app.db",
                       connect_args={"check_same_thread": False})
SessionLocal = sessionmaker(bind=engine, autoflush=False)


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]


Base.metadata.create_all(engine)

app = FastAPI()


def get_db() -> Generator[Session, None, None]:
    """升级版：一个请求一个事务——正常自动 commit，异常自动 rollback"""
    with SessionLocal() as session:
        try:
            yield session
            session.commit()        # 接口正常结束 → 提交
        except Exception:
            session.rollback()      # 接口抛异常 → 回滚，再继续抛出
            raise


class UserCreate(BaseModel):
    name: str


@app.post("/users", status_code=201)
def create_user(data: UserCreate, db: Session = Depends(get_db)):
    user = User(name=data.name)
    db.add(user)
    db.flush()                      # 只 flush 拿 id，不提交——提交权在 get_db
    return {"id": user.id, "name": user.name}


@app.post("/users/boom")
def boom(db: Session = Depends(get_db)):
    db.add(User(name="半成品"))      # 操作①：写入
    db.flush()                      # SQL 已发出，但事务未提交
    raise RuntimeError("操作②炸了")  # → get_db 捕获异常 → rollback → 客户端收到 500
```

启动并验证：

```bash
fastapi dev app.py

# 正常接口：事务被 commit，数据落库
curl -X POST http://127.0.0.1:8000/users -H "Content-Type: application/json" -d "{\"name\":\"张三\"}"
# {"id":1,"name":"张三"}

# 异常接口：返回 500，事务被 rollback
curl -X POST http://127.0.0.1:8000/users/boom
# Internal Server Error
```

最后直接查库，确认"半成品"没落库：

```python
import sqlite3

with sqlite3.connect("app.db") as conn:
    print(conn.execute("SELECT id, name FROM users").fetchall())
```

预期输出：

```text
[(1, '张三')]
```

要点：接口里只 `add`/`flush` 不 `commit`，事务边界完全由 `get_db` 收口——这正是第五节"谁代表完整业务谁 commit"在 Web 框架里的样子。

</details>

## 📝 本节小结

- 事务 = 一组同生共死的操作；Session 的操作天然在事务中，commit 定边界
- 推荐 `with session.begin():`——自动 commit、异常自动 rollback
- commit 失败必须 rollback，否则 Session 罢工
- 底层函数不 commit（最多 flush），**谁代表完整业务谁 commit**
- 并发扣减用 `with_for_update()`（悲观锁）或条件原子 UPDATE
